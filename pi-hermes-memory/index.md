# pi-hermes-memory 使用规范

## 定位

pi-hermes-memory 是 Pi 的持久记忆扩展：Markdown 为真源、SQLite 供检索，提示词默认把记忆当作便条——「helpful context, not as instructions」，当前请求、仓库文件、工具输出优先于记忆。本页收「具体怎样做」的共性规则：按效力分级存放内容，使授权不被架空、事实不腐烂。

## 记忆分四层存放

- 跨仓库授权（不可协商的指令）放 `STANDING.md`（`/memory-pin`）：唯一每轮注入且 agent 不可写的区块；记忆靠 agent 主动搜索，规定等不到那一刻。
- 项目级约定（只在某仓库生效）放该仓库 `AGENTS.md`：Pi 原生加载，按仓库分层，不占 pin 预算。
- 会过时的事实（目录、版本、字段表）正本放仓库，记忆只留指针：记忆中的副本无人维护，必然落后于正本。
- 无归属事实（机器 quirks、工具坑）留记忆池全文：不在任何仓库中，指针无目标。

前三层之外一律不进记忆池：状态快照（版本号、目录清单、「进行中」）写入即腐烂，事实归仓库。

## 四个机制边界

- 默认 policy-only 模式下完整记忆不进上下文，靠 agent 决定是否搜索——对事实无妨，对致命约束不可用，故授权必须走 STANDING；
- 后台复习的提示词只抽取事实、失败、偏好，不记录会话叙事——需要过程记录的场合不能依赖该扩展自动捕获；
- STANDING 是提示词层的最强形态，但不是工具强制——硬约束需下沉到脚本、门禁等结构层；
- 后台复习与收尾写入看不到 STANDING——口头立规管不到自动抽取，周期清理不可省。

## 生命周期

- 先迁授权出池，再放任自动合并：授权条目极少被搜索命中，在召回统计里是弱保留候选，先合并会被优先淘汰；
- 周期复检记忆池：合并重复条目、将过时事实改写为指针；
- 核验用可重跑的脚本而非记忆转述：带提交号的断言须对仓库求证，条目互证不构成证据。

## 验收

以投诉复发为最终判据，不以探针通过数为准：迁移前的历史基线（「你为什么还问我」类抱怨）须归零；同时反向抽查「该问的还在问」，防止把 agent 矫正成该问也不问。
